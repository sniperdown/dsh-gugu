# 长驻资源的生命周期：谁负责收场

> 本文是一份检查清单：**插件里所有"活过一次调用"的东西，是不是都登记了收场。**

---

## 为什么要做这件事

当天排查「内部通道有的时候灵，有的时候不灵」，根因是：

**`ctx.effect` 的清理里漏了收件箱** —— 每次插件重载（配置 live reload、HMR 等）
都多留一个轮询器，好几个实例抢同一个 `.offset` 文件。
**消息没丢**，但"由哪个实例消费、能不能轮到"是不确定的。

**共同的教训**：

> **不要指望「对象被丢弃 = 资源就没了」。那个假设对闭包不成立。**

`createAliceInbox()` 返回的是一组闭包 —— 外层对象丢了，里面的 `setInterval` 还在跑。
（诊断日志里的证据：`apply` 在同一秒内被调用过 9 次，每次都新建一个轮询器。）

---

## 排查结果

### 已正确登记的（占绝大多数）

| 资源 | 登记方式 | 收场 |
|---|---|---|
| 空闲会话释放 | `ctx.effect` + `ctx.interval` | Cordis 自动 |
| 心情平复 | 同上 | Cordis 自动 |
| `session/event` 监听 | `ctx.effect` + `ctx.on` | Cordis 自动 |
| web 路由 | `webCtx.effect` | Cordis 自动 |
| **收件箱轮询器 ×2** | 关停 effect 里 `.stop()` | 显式（**当天补的**） |
| 会话上下文监听 ×4 | `binding.dispose()` → 逐个 `handle.dispose()` | 显式 |
| transport 的 4 个转发监听 | `gateway.detach()` → 逐个 `off` | 显式 |
| 重连定时器 | `transport.stop()` → `clearTimeout` | 显式 |
| 反向 WS 的 http server | `ReverseTransport._shutdown()` → `server.close()` | 显式 |
| 正向模式的 socket | `ForwardTransport._shutdown()` → `socket.destroy()` | 显式 |
| HTTP 传输 | `HttpTransport._shutdown()` → `alive=false` + `pending.clear()` | 显式 |

### 当天补上的两处「靠对象被丢弃」

| 资源 | 之前 | 现在 |
|---|---|---|
| 学习回写的防抖定时器（`saveLearnedTimer`） | 卸载后仍可能跑一次、写一遍记忆 | 关停时 `clearTimeout` |
| 调试快照的 2 个 transport 监听 | **匿名函数，没法 `off`** | **具名**，关停时显式 `off` |

**为什么必须修**：它们当时"没出事"，只是因为**碰巧**每次重载都新建 transport / 闭包。
一旦将来有人把 transport 改成复用（**省重连开销是很自然的优化**），
这两个监听就会**每重载一次累积一份** —— 而那正是 inbox 那个 bug 的形状。

## 排查同类问题的检查表

| # | 找什么 | 问什么 |
|---|---|---|
| 1 | `setInterval` / `setTimeout` | **有没有对应的 `clear`**？（短命的请求超时不用管；**跨越调用边界**的才要） |
| 2 | `.on(` / `addEventListener` / `.watch(` | **有没有对应的 `off`**？**监听器是不是具名的**（匿名的话你还 `off` 得掉吗）？ |
| 3 | `.start()` | **有没有 `.stop()`**？ |
| 4 | 自己开的 socket / server / 文件句柄 | **有没有 `close` / `destroy`**？ |
| 5 | `Map` / `Set` 当缓存 | **有没有上界**？（这类泄漏不报错，只是内存慢慢涨） |
| 6 | **用的是 `ctx.effect` 吗** | 用了 Cordis 帮你收；**没用就得自己想清楚谁收** |

**第 6 条是重点**：Cordis 提供了 `ctx.effect` / `ctx.interval` / `ctx.on` 这套登记机制，
**用它能省掉"自己记得收"这件事**。当天漏掉收件箱，就是因为它**是后来加的**，
而**没人回头检查"新加的长驻资源有没有登记进清理"**。

> **加东西的时候要顺手问一句：它靠什么收场。**

---

## 一个更一般的判据

这次排查里最有用的一个区分：

| 资源的寿命 | 要不要显式收 |
|---|---|
| **短于一次调用**（请求超时、`await sleep`、单次重试） | 不用 —— 它自己会结束 |
| **跨越调用边界**（轮询、监听、连接、长定时器） | **必须** —— 而且**不能靠"对象被丢弃"** |

判断方法：问一句「**这次调用返回之后，它还会动吗？**」
会动 → 它就得有个明确的收场路径，而且要能被**卸载时**触发一次。
